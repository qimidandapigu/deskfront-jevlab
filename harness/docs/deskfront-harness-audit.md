# Harness 战术执行链审计与修复

范围：quickplay-harness 的 Deskfront 指挥、执行、空间工具、动作反馈，以及用户在 deskfront-jevlab 中新增或修改的游戏适配。保留通用运行器与其他游戏的独立行为。上游 deskfront-jevlab 基线和未改动的原始实现保持不变；用户自有改动可以重构。详见 [所有权与模块化边界](deskfront-ownership-boundary.md)。

## 已确认的故障链

1. 单兵请求时取得位置候选，模型选择后，Harness 再次生成列表并逐字段精确匹配。
2. 候选每秒更新，依赖单位位置、敌人位置、队友占位及排序。原位置不在新列表，不等于位置不可达。
3. 此前匹配失败被改成 wait。旧局 green-1 在10.7/12.7秒、green-2在10.9秒已选择撤离，却没有下发移动。
4. 调用日志保留模型原始 move，实际执行却是 wait，显示 pending，妨碍归因。
5. 独立局部射位排名没有近期位置历史，火箭兵反复在附近前后移动。

## 本次实现

- execution_validation.py/gd：对模型原选定目的地请求原生导航检查，返回局次、请求ID、可达性、路径长度及拒绝原因；不按最新榜单判定有效性。
- 检查保留单位存活、局次、目的地可走、队友占用、队友预留、原生路径末端距离。最长等待0.8秒，超时明确拒绝，不冒充成功；该等待不触发额外模型调用。
- 每次记录 execution-resolution：requested、actual、validation、origin、command_id 和真实提交状态。原始回答与实际动作分开，未提交不再一直伪装 pending。
- 保存最近20秒位置，给重复射位明确往返警告并降低本地规则分数；模型仍自行决定是否返回，不强制覆盖其战术选择。
- 保留早期风险、短途避火位置、恢复、原生射击检查以及2秒/20秒节奏。

## 仍有的系统限制

- 几何可达不等于沿路安全；移动验证不预测敌人的未来位置。
- 射位工具以站姿射线估计，真实炮口/姿态检查仍可能否决开火。
- 共享任务板目前是已选动作与实际火力记录，不是原子的小队任务分配协议；同时冲旗与先后接替仍需实战改进。
- 重伤/压制后的原生爬行仍存在；不以取消动画掩盖战术失误。
- 红方原生AI可能停滞，不应单靠一局胜利评价模型优势。
- 本次不承诺已消除所有往返；新增信息必须看实战是否采纳。
