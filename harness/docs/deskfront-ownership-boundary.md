# Deskfront 所有权与模块化边界

日期：2026-10-02

## 结论

Deskfront 的模块化范围按代码所有权判断，不按仓库目录判断。

- `C:/game/deskfront-jevlab` 的 `origin/main` 是上游基线。基线中未被用户修改的实现保持原样。
- 用户在 `deskfront-jevlab` 工作树中新增或修改的游戏逻辑、适配、补丁、测试和文档属于本项目代码，可以重构。
- `C:/game/quickplay-harness` 中的 Harness、staging、viewer、模型接入、回执、测试和文档属于本项目代码，可以重构。
- Godot 引擎程序、版本和外部依赖不属于本项目代码，不做引擎级重构。
- `assets/**/*.import` 和脚本旁的 `.uid` 是 Godot 生成的元数据，不作为职责模块化目标；需要时通过资源/脚本导入流程重新生成。

## 事实源

原生游戏改动是游戏机制事实源：单位状态、战斗、武器、坦克、迫击炮、动画和已经写入游戏的玩法规则以 `deskfront-jevlab` 中的用户改动为准。

Harness 负责协议、模型调用、指挥调度、观察、回执、会话、测试和 staging 装配。Harness 的 Godot overlay 只实现 Harness 专属的临时注入和模式适配，不复制一套与原生游戏长期并行的战斗机制。

## 重构规则

1. 先保留公开入口、场景节点名、命令协议、快照字段和真实回执。
2. 只移动用户新增或修改的职责；上游未改动代码继续作为上下文，不主动重写。
3. 原生游戏中的拆分必须回到 `deskfront-jevlab` 的事实源；Harness staging 只同步接口和必要的模式覆盖。
4. 每次拆分后运行原有 Godot 语义检查、Harness 回归和 staged 编辑器加载检查。
5. 低风险顺序为：用户新增小队模块 → 游戏适配工具 → `game.gd` 的 UI/命令边界 → `unit.gd` 的表现与感知 → `combat_fx.gd` 弹道 → `battlefield.gd` 导航与掩体 → 其余宏战术。

## 当前审计基线

当前原生仓库 `HEAD` 与 `origin/main` 一致，工作树中的语义改动集中在游戏脚本、工具、数据、测试和新增小队脚本；大量 `.import` 文件属于生成元数据。后续审计继续以 `origin/main` 和工作树差异为准，不把未改动的上游文件列为重构目标。
