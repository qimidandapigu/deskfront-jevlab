# 无尽推进：体验分析、关卡策划与空间搭建

本页为生成子系统当前职责说明，替代旧文档中的“战斗期间预生成”和“单次JEV选择完整套餐”。同一套Harness的三种Agent职责，不是三套模型客户端。

## 决策输入去重（2026-09-30）

本轮只改变 JEV 请求视图，不修改作者卡、模型可选项、编译操作或原生导航。`decision_views.py` 为策划和搭建生成只读副本，原始设计与回执仍完整保存。

- 历史逐格物件列表与 `visual_identity.material_counts` 完全一致时，仅去掉重复计数；整关 `materials` 与 `material_profile.counts` 完全一致时同理。保留比例、来源、实际物件、路线、战果和未知值。各格相同的 `props_basis` 共享一次；不同来源仍逐格对应，不混同观测与编译事实。
- 策划继续输出完整方案并额外给出 `spatial_goal`：战术关系、空间构图、文具意图、完整下一关目标。搭建请求直接读这份目标和任务／兵力，不重复发送由同一选择展开的长指令及任务书元数据。九桌的用途、主物件、作用、邻桌关系仍完整保留在共享输入及每题直接说明中。旧任务没有 `spatial_goal` 时原样保留其特别指令。
- 全部卡片、方向、单物件参数、精确几何和朝向证据继续提供。没有新增模型调用、压缩模型或后台工具；投影只在已有请求发送前运行。`mock` 仍读取原来的完整数据。

### 第二轮：空间请求字段消融（`region-builder-v14`）

卡片完整行、精确物件坐标／尺寸、方向证据、九桌任务书和最近成图仍保留。初稿与批量修改只移除单物件编辑才需要的 `asset_catalog`、素材尺寸列名和编辑列说明；这些字段在 `prop_edit_details` 中仍完整提供。所有 26 张卡和每张卡的方向选项都保留，没有做候选过滤。

曾试验把完整卡片行换成“用途、主物件、大小、高低”的语义摘要，也试验压缩历史逐格数据。真实普通关 A/B 中，摘要版稳定地多触发一次单物件编辑，并出现用途／主物件少一格的结果；历史摘要也可能改变编辑动作。因此这两项只保留为实验代码，不进入默认运行时。当前默认只启用低风险的字段消融。

最后保留的低风险版本只把素材目录从 `[名称,宽,深,高]` 改为 `[名称]`；卡片内的每件物件仍保留精确宽深高和偏移。两组真实 JEV 对照中，空间输入从 132,473 降到 128,210，约减少 3.2%；两组均保持两次请求，普通组用途／主物件匹配保持 8/9、9/9，营救组为 8/9、7/9。营救组的卡片数量有正常模型波动，但没有触发额外单物件编辑。这个收益小于语义摘要，但更符合“不影响效果”的要求。

下一步若继续压缩，只做单变量实验：移除初稿阶段未使用的桌面中心坐标、重复的接口说明和批改回执中的重复统计；保留完整卡片几何、方向证据、失败原因和最近素材历史。不会先引入 LLMLingua 或 TOON；它们尚未在 JEV 的卡片选择任务上证明质量不下降。

本轮冻结当前作者库做前后对照：它有 26 张普通卡、每格 104 个卡片方向选项，与下方 24 张版本的旧报告不同。前后使用同一库，不用跨库数字计算压缩率。

## 无尽推进兵种接入（2026-09-29）

- 所有无尽模式步兵新增近距离反坦克炸药包：只对可见敌方坦克开放，最大投掷距离 0.44 米，按真实枪口到坦克的路径和友军爆炸安全复核；投掷动画释放时生成独立包状弹体，命中后由原生爆炸、遮挡与装甲方向结算。每兵冷却 14 游戏秒，不消耗普通手雷；侧栏悬浮提示显示剩余冷却。参数为 110 基础伤害、1.2 装甲倍率，前侧装甲仍有区别；不是远程指定扣血。Soldier Agent 在可投距离内获得动作和坦克目标，较远时可看到经原生寻路检查的短程接近候选；新出现的坦克接近／投掷机会会提前唤醒一次个人复核，是否冒险仍由模型选择。拒绝、发射和冷却以 Godot 回执与快照为准；当前普通坦克生成条件仍保留火箭兵反制要求。

- 绿色开局三人为一名步枪兵、一名冲锋枪兵、一名火箭兵；首段是三对三。后续补员优先补齐已损失的火箭兵／冲锋枪兵；救援关被困士兵携手枪，加入后仍使用真实手枪射程与伤害。手雷和刺刀继续属于单兵动作，不另算兵种。
- 六个守军位置仍由 JEV 搭建并选择人数；JEV 策划在同一次调用里另选 `defender_mix`（均衡守备、步枪前哨、近距巡逻）和 `support_type`（普通步兵、火箭兵或坦克）。守军编成决定步枪、冲锋枪、手枪的实际部署；选择火箭兵支援时，一名守军改携火箭筒。首段只开放普通步兵，后续有友方存活火箭兵时开放坦克。这些选择进入实际构建命令、引擎任务和回执，反坦克炮不进入兵种池。
- 选中坦克时，引擎在新区域坦克可通行网格上寻找不与步兵重叠的敌侧停靠位置。找到才实体生成坦克炮单位，并将其 ID 列入必须清除的本段守军；找不到则记录 `no_clear_tank_staging_point`，不假报部署。坦克采用原有车辆导航与瞄准，即使红方步兵由 Harness 指挥也不交给 Soldier Agent。坦克在无尽模式为 240 生命值，以避免沿用旧 420 生命值把单名火箭兵拖入过长战斗。反坦克炮不参与无尽推进的生成。
- `secondStageTankShowcase` 是默认关闭的演示选项：JEV 正常生成首关，引擎明确记录“跳过首关交火”的回执，随后第二关只向 JEV 策划提供坦克支援目标；九桌素材与空间搭建仍由 JEV 完成。坦克入场后暂停供查看。该演示不代表绿色小队实际打赢了第一关，也不改变普通模式的支援选择。
- `secondStageTankRule` 是当前无尽推进版默认开启的规则：首关正常交火，第二关固定选择坦克支援，但九桌布局和守军编成仍由 JEV 设计，也不会自动暂停。若首关火箭兵阵亡，第二关兵力方案必须补一名火箭兵；引擎在部署坦克前核对这名援兵。只有首关实际清场后才有第二关，规则不会伪造胜利。回归旧场景时才显式传 `false`。
- 当前原生验证覆盖装备、坦克真实生成、任务未提前完成与击毁后结算；是否更有观赏性及不同 JEV 关卡里坦克实际出现频率，仍需真实连续对局评估。

## 当前实现：24 张精品卡与完整九桌任务书（2026-09-29）

本节优先于下方历史记录的 45 张、中心通路和分开选择方向的描述。

- 作者库为 24 张普通卡，覆盖八种用途和 21 种已有素材。当前 5 张单物件、19 张双物件；同一种物件在所有当前卡片和添加、替换操作中使用同一套宽深高。纸盒、电脑、打印机采用更大的固定尺寸，书册更薄，手持工具保持较小比例。渲染不再按摆放位置旋转后缩小。各类轮廓、固定配色、尺寸和最新原生证据见 [文具视觉规范](deskfront-stationery-art.md)。每个九桌区域另有一件无碰撞装饰。模型看到最终物理尺寸，引擎不会在提交后再缩放、换物件或去重；旧 ID 保留读取历史回执。

- DeepSeek 继续分析当前战况与下一关目标。JEV 策划一次选择完整九桌意图编排：每桌用途、实际可组合的主物件、作用和邻桌关系。候选包含不同工作流程及明确延续近期的选项；它们不指定具体卡片或禁止其他卡片。
- 策划请求中的候选表只逐格传用途和主物件；通用用途职责及“同用途相邻格连续、异用途交接”的解释共享一次。JEV 选定后，程序按该方案展开完整的逐格职责和邻桌关系，再交给搭建员；这只压缩重复描述，不更改所选九桌方案。
- JEV 搭建先做两次调用：初稿每格选择一个“卡片＋方向”完整选项（24×4＝96），九格同批；批改读完整初稿，每格选择保持、完整换卡与方向，或单物件编辑动作。移除动作在同一选项中指定物件；只有添加、移动或替换需要新位置／素材时，才追加一次只针对被选中格子的参数请求。未选中的格子不再重复询问物件、坐标和方向。单件卡恢复四个朝向。普通推进改为从六种整图连通骨架中选择通路，救援仍由 JEV 逐接口选择以兼容堡垒与出口的联合校验；入口和出口均由 JEV 选。骨架菜单优先排除与最近两关少于三处接口差异的选项；若无候选，则仅避开上一关；仍无候选才恢复全菜单。救援普通格按实际 cell 编号作答，所选堡垒格的普通答案明确不执行。
- 官方接口明确同批问题并行、相互独立；因此这不是九格联合 JSON 生成。先确定整份任务书，使所有搭建题看到同一已确定分工；原子卡片方向选项避免引用同批尚不可见的角度答案。批改之间仍无法互相看到新答案，不能保证最终一定不重复。参见 [JEV 原语](https://docs.typesafe.ai/primitives) 和 [Choice](https://docs.typesafe.ai/primitives/choice)。
- 物件可占桌心。Python 与 Godot 依据最终几何计算真实通路、站位和增援点，救援墙加入后再计算一次。详见 [几何导航](deskfront-geometry-navigation.md)。本地 Bot 一次跳过连续已到达的短路点，不再每 0.8 秒只消耗一个点；该分支不控制 Harness 接管的单位。
- 常规保持、整格换卡、转向或移除时仍为策划、初稿、批改三次 JEV；选中添加、移动或替换单件文具才有第四次参数请求。该请求只带目标格的卡片几何与必要的参数题。接近请求预算上限时不提供无法支付的单物件动作，但仍保留全部九格的完整换卡与旋转选择。卡名、完整几何和九桌任务书在每次调用内共享；每道题引用共享表。
- 2026-09-30 的用量优化只缩短重复出现的候选编号：`p013` 表示共享表 `card_01` 旋转 270°。九格仍在一次调用内各选完整卡片与方向，候选数量和引擎原样执行约定不变。曾试过先选修改格、再只展开所选格的两步批改；真实 JEV 在同一历史初稿上标记六格换桌，随后六格都选回原样，修改用量反增，因此没有启用。缩短编号后的独立真实搭建调用用量为 86,916 token（初稿 41,160、批改 45,756），两次请求约 4.7 秒；可与此前相近关卡的搭建用量 98,746 token 比较，但模型选图并不完全相同，不能据此宣称画面质量已提高。回执见 `output/compact-world-full-20260930.json`。
- 同日进一步采用 `region-builder-v13` 请求格式：`templates` 仍按卡号查找，各行依共享的 `template_columns` 读取，物件数组依 `template_item_columns` 读取。所有名称、用途、主物件、方向、通道和原始几何均保留；九格每题的候选集合和顺序不变。通用要求移入 `draft_choice_rule` / `revision_choice_rule`，但每道题仍直接写出该格用途、主物件、作用和邻桌关系。删除每题的具体任务、只让模型间接查表的首版，在两个普通推进样本里降低了任务兑现程度，未保留该做法。近期历史和空间描述没有做摘要或英文改写。
- 模型输入的技术预览仅移除网格计数、导航算法标识及已在 `draft_ports` 中出现的入口出口；失败原因、区域锚点、连通关系、静态射界依据与守军预览保留。日志和最终技术回执仍完整。单物件参数请求不再携带只服务于整图选卡的重复说明。
- `output/payload-lowrisk-20260930/report-final.json` 保存三组真实前后对照：一组营救、两次相同坦克遭遇任务。只计空间搭建，不包含新规划、DeepSeek、战斗、情绪或解说。两轮核心请求输入合计从 199,847 减至 190,067（4.9%）；计入这批样本中旧版发生的两次单物件参数请求，全部输入从 212,581 减至 190,067（10.6%）。后一个比例依赖模型是否选择单物件编辑，不能保证每关如此。新版每关两次模型调用合计约 0.86–0.95 秒，调用冷热及服务状态不同，不能据此声明固定加速比例。
- 三组新版结果均通过 Python 技术检查；用途匹配均为 8/9（与旧版一致），主物件匹配为 8/9、9/9、9/9（旧版三组均为 8/9）。匹配只作诊断，不筛选或修改方案；堡垒也计入九格，因此不是任务质量的完整评分。固定历史答案回放的操作、候选菜单、方向证据、历史和完整回执完全相同。49 项直接相关检查通过；全量 130 项检查另有三项失败、一项错误，使用改动前源文件复现一致，涉及既有纸盒摆放、遮挡阈值和堡垒几何，不属于本次请求压缩引入的回归。本次未启动 Godot 实战，不能用这些对照证明视觉或战斗体验不变。此前输入减少 20%–30% 是目标，本次没有达到。
- 整图骨架现在是一次 JEV 选择，而非十二个互相独立的接口选择。Godot 按该骨架的真实主通路绘制静态桌面色带，并给不同骨架使用不同的柔和桌面配色；连续地面、碰撞和导航不靠颜色变化。色带和桌面在同一预览中生长，不增加逐帧绘制或模型调用。此视觉编码用于提示整图差异，不能证明玩家已经感到不同；需要连续关卡截图和试玩验收。

质量与重复统计只作回执，不触发引擎换图。单物件多字段仍受现有 typed-choice 接口限制；未实现任意连续坐标或任意九格联合生成。

当前美术与固定尺寸卡库总览见 `output/stationery-identity-stage/engine/output/world/curated-catalog-24.png`。单件卡仍只放一件，但与双件卡中的同类物件等大；所以单件桌面会更空。测试和真实调用的结果应区分：作者几何检查、原生导航、真实 JEV 编译预览、完整实战分别提供不同证据，不能互相代替。

### 历史验证与剩余边界（以下实测早于素材身份美术更新）

本次统一物件尺寸的 Python 卡片、几何、组装、任务书与模型选项检查分别为 4/4、4/4、5/5、10/10、11/11。Godot 对本版重新生成的 134 项几何回执和 8 张区域图回执均通过，5/5 个原生单位行进案例到达且没有穿物件或离开桌面。上一版完整后台会话不作为此次统一尺寸版本的实战证据。

## 整关差异与历史反馈（2026-09-27）

DeepSeek 在当前关进行时读取当前任务的真实九格布局（优先来自原生 `mission.spec`，必要时按 operation ID 查建成回执），同时观察战况，在 `next_goal.layout_change` 写明下一关具体要改变的路线或文具遮挡关系。Godot 快照里的整数旋转可能序列化为 `0.0`；分析副本把它还原为整数以供 Python 编译，绝不改建造命令。

关卡策划 JEV 在原有同一次请求里，除任务、兵力和战术关系外，还选择整关空间形状（北/南迂回、双线、中央突破、错列掩护、敌侧据点）及文具视觉主题。它输出的是搭建意图，不指定九格的具体设计卡。空间搭建 JEV 仍一次选择九格、方向和每条相邻接口是否通行，随后一次批量修改；场景形状会转成每格不同的任务描述，主题仅调整少数重点格的菜单示例顺序，45张普通卡始终全部可选。真实模型看到中性卡片编号和完整物件说明，选定后才精确映射回引擎内部卡号；避免把 `flank_0` 这样的技术编号当成文具选择依据。

最近最多三次**已建成**的关卡现在以事实摘要同时提供给策划和搭建：每格选过的卡、方向和文具，实际组件材料，入口出口、连接、路线、静态暴露预览以及可用的任务结果。它不再只看到“九格是否启用”。搭建回执额外记录与这些关卡的构图相似度，综合每格卡片家族、材料、连接和入口出口；这只是诊断，不会删选项、强制去重或替 JEV 换卡。卡号不同但同属旋转家族时不会被当作完全不同的设计。

首轮真实 JEV 后台样本连续三关的近期构图相似度为 0.941、1.000，证明仅添加历史摘要与策划主题不足以打破常用卡偏好。随后在初稿每格选项上标出最近使用次数，并把初稿相似度传给同一次批量修改请求；第二轮真实 JEV 样本建成两关，第二关对第一关相似度为 0.860，出现一格抽纸/杯子/尺子卡，但整体仍明显偏向通用 flank/defense/advance 家族。这些是少量后台样本，不能证明长期改善或视觉验收。

第三轮将真实 JEV 的卡片选择项改用中性编号并保留完整物件、位置与遮挡描述，精确映射回原引擎卡片；没有删减候选。该轮两张已建成图的相似度仍为 0.926，且一次最终稿因90°/270°卡片组件越界无法建造。这说明当前的45张卡（其中32张只是8种战术摆法的方向变体）和固定九格全连通结构仍会造成审美与打法收敛；不要声称这轮已解决关卡雷同。引擎只拒绝不可建造的最终稿，没有代 JEV 修补或选新图。

最后一轮真实后台样本中，DeepSeek 的输入确实包含当前关9格与12条连接，并明确指出入口/出口防御卡重复、推进卡家族三次出现；JEV 的下一张已建成图增加了鼠标转角与打印机工作台，和上一图的构图相似度为0.620，关卡生成约2.1秒。一次生成因等待期间兵力变化被 Harness 放弃，重试后建成。该样本说明反馈链路可以发挥作用，不证明长期关卡审美或战斗路线已稳定改善。JEV在本轮仍选择12条接口全通，接口自由度尚未被实际利用。

该改动没有新增模型请求：策划一次、搭建初稿一次、搭建批量修改一次。历史摘要增加上下文长度，实际模型耗时、跨关观感和战斗差异仍需真实 JEV 多关回放确认；结构测试不能证明最终体验已改善。

## 历史：整图模板选择与批量修改（2026-09-24，45 张版本）

DeepSeek在**当前关进行时**分析战况：新关约5秒后首次观察，之后约20秒更新，同时给出下一关的体验目标、战术问题、应避免的重复和路线偏好。短关卡若在首次观察前结束，清场后对**刚结束的当前关**补一次分析，再由策划JEV读取报告及最终清场事实；报告较旧时，最终伤亡和任务状态优先。首关尚无体验报告，按初始状态启动。策划与搭建是两种JEV任务角色，并非两个独立模型客户端。

空间搭建JEV一次提交左侧入口、右侧出口，以及全部9格的模板和0/90/180/270度旋转。每格从45种几何上不同的普通摆法中选择，包括基础双侧掩护区、档案纸盒占地格和多种文具遮挡格；**不限制启用格数**。45张设计卡从引擎共享的模块几何生成，给出真实物件、相对位置、宽深高和有效遮挡数量。可通行的44张卡每张至少有3件宽度不少于0.14米、高度不少于0.07米的有效遮挡，有效遮挡占地至少0.04平方米；封闭格是仓库障碍物，不计为可通行掩体。原始库有大量相同几何的重复角色/接口编号，菜单只展示明确的45张普通卡，仍允许JEV选择任意一张。

JEV执行接口目前只支持类型化选择题，不支持一次返回九格JSON。初稿仍是一轮JEV请求，但九格分别有入口、中央、侧翼、敌侧等具体任务，每题保留全部45张卡，仅将适合此处的示例排在前面。第二轮给JEV重复卡数量、各格遮挡数量及技术预览；重复格的“换卡”选项更显眼，JEV仍可选择保留，Harness不强制去重、不替换它的最终结果。最终回执记录实际不同卡数、最大重复数和卡片分布。

救援任务在同一次初稿请求中改为先选右侧三格中的堡垒位置，再为另外两个右侧格以及左、中六格选普通摆法。堡垒格是一个明确的目标格，最终叠加7件文件墙；因此不会让JEV误把三个右侧格都当堡垒。它同时决定本关出口，不固定为中间格。第二次请求可批量修改其余八格；堡垒目标格保持选定位置。

救援外围守军现在根据最终文具和堡垒墙占地预约附近空位，不再使用会与打印机、电脑卡相撞的固定坐标。Python用264组“堡垒位置×相邻普通卡”做了通路和部署检查；Godot仍独立重放。2026-09-27的一次真实JEV救援样本最终使用6张不同普通卡（最大重复2格），包含打印机和笔记本电脑，收到Godot的`completed`回执。这只证明该样本可以运行，不能证明长期关卡审美或战斗体验。

初稿形成后，搭建JEV在第二次请求中同时收到完整9格设计、接入点、主路/侧路、各部署的守军预览与技术回执。它一次提交全部9格的最终修改：每格可保持、换模板、旋转、增加一件文具，或移动、移除、替换模板中的一件文具；还可改入口、出口和部署。这是一轮批量修改，**每格最多一个修改动作**，不是9次串行模型请求。当前JEV接口使用`choice`，所以新位置与旋转采用离散档位。物件尺寸、碰撞由共享库决定，不能自报尺寸或注入代码。

Python对初稿只返回可建造性和静态战术预览，不修改也不否决初稿；最终稿只做占地、碰撞、通路和部署等技术检查。静态暴露、重复文具和审美评价不会替JEV改图。技术上无法建造的最终稿会连同原操作和原因记录，不提交给引擎。可建造的最终稿由Godot独立重放；只有原生完成回执算建成。模拟后端保持初稿，不能用它证明JEV的修改能力。

## 调度

- 空场启动：我方4人、没有首关敌人，不记作清场。立即使用初始体验参数调用JEV策划与搭建，首场实际战斗部署3名敌人，不等待DeepSeek。

- JEV返回后只做技术可建造性检查，不提供质量修复选项；方案进入引擎之前复核会话、区域版本、兵力、暂停状态。
- 引擎独立重放组件操作并验证通路、碰撞、出生点；0.5秒展示后再次复核并提交。仅原生完成回执算建成。

## 历史阶段边界（45 张版本）

当前仍是3×3单层桌面、45个普通模板、救援堡垒目标格、每格一轮修改和有限部署方式；尚不能让JEV发明新物件、直接画任意连续几何或在同一格修改多件。入口/出口位于左右桌边，其他格可以全选或留作档案纸盒占地。守军站位根据实际文具占地预约空位，不再固定压在文具上；只检查可建造性，不替JEV改模板。区域尺寸与多层空间尚未扩展，交叉火力优势仍需战斗回执验证，不能由连通性测试替代。

下一项几何问题已量化：44张可通行卡的0°整图都可建造，但其中14张卡在90°/270°整图测试中碰到边界或部署点。模型本次实际选择0°，所以这次救援成功没有覆盖横向旋转。应先把这些朝向设计成可建造的卡片姿态，再做多关视觉回放和不同卡片被选频率的统计；不能只靠提示词声称四个朝向都能用。

几何校验不证明侧翼战术必然发生。双方Bot演示只分析战斗与关卡表现；没有操作机会证据时不声称识别了人类偏好或技能。坦克、新资源事件未在本轮添加。

测试：`python -m unittest discover -s test -p 'deskfront_world*checks.py'`；原生验证脚本由stage安装为`tests/assembly_contract.gd`。

`scenery.gd`负责按用途区分地面色、接缝、胶带标线、平面纸张、包装标签、箱底托板及文件墙细节。它不参与模型调用，也不新增通路上的装饰碰撞，随区域回收一起销毁。实际遮挡由配套的recipe掩体实现。当前仍为单层桌面模块样板，未实现建筑室内、高低差或战损变化。

验收：34组原生地图（含新主题与旋转）共210项检查通过；所有组合模块逐区域旋转也经Python连通性检查。原生验证发现并修正了连续长墙旋转堵住接口的问题，改用门洞结构。

## 历史：整组战术摆放与本地Bot（2026-09-22）

搭建第二步改为从最多12组联合摆放中选择：工具先组合不同区域朝向和守军编成，过滤不可行地图，再给JEV提供区域组件、部署与静态射界估计。它不是分别选每格再猜整体效果。正常仍是策划一次、搭建两次。纵深编成增加前哨、后卫和其他区域分层部署；其他任务可在后场/分区编成间选择。

`tactical_quality.py`使用初始实际人数的部署槽、0.9米射程与0.068米站姿射线，对主路/侧路中心线每约0.06米采样，报告路线长度和暴露比例。有明显差异的候选优先提供；若本图没有则如实保留小差异结果，不声称必有战术优势。这是初始静态估计，不包含移动敌人、姿态、真实武器差异或动态弹道。

本地进攻Bot分成主路与侧翼组，按实际区域路线推进；已有进展时保持任务，受压时可找掩体。守军的换位候选限制在部署点附近0.4米，避免全员追敌导致阵地失去作用。Harness控制的小兵不走这套Bot逻辑。开局集结位置后移，保留文件墙施工安全距离。

原生回归新增真实弹道遮挡与侧翼分组检查；测试通过不等同于实战战术有效性通过。

## 器材区轮廓与接口形状

新增抽屉柜、圆桶、支架路障的引擎原生几何素材（无需外部资源下载）。器材区模块按真实连接口生成直巷、L形、T形、十字或尽头平台，缺角对应实际地面缺失；与原有宽装卸平台混合选择。圆桶使用圆柱外观、保守包围盒碰撞；支架路障目前按整体包围盒遮挡，不支持从支架空隙穿弹。

布局仍在3×3连接节点与当前区域边界内；新增的是不同占地形状和轮廓，未实现任意尺寸的跨格建筑。JEV的整组候选包含模块编号、组合与射界估计，由同一份模块库在Python和Godot编译。装饰不再给新器材错误套用书堆标签。


## Continuous ground and functional industrial kit (2026-09-22)

Region graphs now compile to one continuous 1.8 x 2.1 floor. Unselected cells contain solid warehouses; closed connections between active cells contain visible concrete walls. Graph routes are enforced by obstacles rather than missing ground. Python and Godot consume the same component library.

Six joint kit families: L fortification, U shelter, tank service yard, broken walls and rubble, staggered gabions, pipe loading area. They use compound rectangles, leaving doorways and centre routes open. Tank and pipe collision remains a conservative bounding box; this is not mesh-perfect collision. Warehouse windows are visual details, not firing apertures. External Kenney/Quaternius packs researched but not imported.

Validation: 32 native geometry fixtures, host/native parity, reachable deployment, real opaque-cover ray blocking. Combat quality and visual polish remain separate live acceptance requirements.
